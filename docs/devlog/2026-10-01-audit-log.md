# 2026-10-01 破坏性操作审计日志（P0 #7）

批次内容：`x` 的破坏性操作（进程 kill、端口回收、服务动作、原生逃生舱）
在真实运行时逐条追加写本地 JSON-lines 审计日志。x-core 新增纯模型
`AuditEntry` 与手写的 UTC RFC 3339 格式化；x-platform 新增 `audit` 模块
（路径解析、写入、三个装饰器）；x-app 组合根 `attach()` 挂接。

## 为什么挂在组合根而不是各平台 manager()

**现象/决策**：审计装饰器可以包在每个 `<os>::<domain>::manager()` 里，也
可以只包在 x-app 的 `create_context()` 之后。选了后者。

**原因**：CLI 的集成测试（`crates/x-cli/tests/cli.rs`）和 TUI 测试都用
`x_core::testing` 的 stub 自己拼 SystemContext，根本不经过 x-platform；
把装饰放组合根意味着测试永远不写真文件，而真实二进制（含 TUI 里的
kill）全都留痕。反过来若包在 manager() 里，装饰逻辑本身能测，但"测试
不污染磁盘"要靠纪律而不是结构保证。

**代价**：`x_platform::create_context()` 直接调用者（未来若有）不审计；
目前唯一调用者是 x-app main，可接受。

## 手写日历换算必须用钉死值测

**现象**：x-core 不想拉 chrono，`rfc3339_utc(secs)` 用 Hinnant 的
days-from-epoch 算法手写。

**处理**：单测钉死四个已知值——epoch 0、1 700 000 000
（2023-11-14T22:13:20Z）、951 782 400（2000-02-29，世纪闰年）、-1
（1969-12-31T23:59:59Z，负秒数走 div_euclid/rem_euclid）。这类纯函数
"看起来对"和"边界对"只差闰年与负数两处，各钉一发。

**证据**：`cargo test -p x-core audit` 7 项全绿；`now_utc_rfc3339()`
长度 20、以 Z 结尾的弱断言只做形状哨兵。

## Arc::clone 与 unsizing 强制的坑

**现象**：测试里
`let inner: Arc<dyn ProcessManager> = Arc::clone(&stub);` 编译失败
（expected `&Arc<dyn …>`, found `&Arc<StubProcess>`），但结构体字面量里
裸写 `inner,` 却能强制。

**根因**：`Arc::clone` 是泛型关联函数，T 由**期望类型**反推，期望
`Arc<dyn Trait>` 就要求参数也是 `&Arc<dyn Trait>`；方法语法
`stub.clone()` 先按接收者定出 `Arc<StubProcess>`，再在 let 位置做
unsizing 强制。赋值/字段这类"值强制点"行，函数调用实参不行。

**处理**：测试统一写 `let inner: Arc<dyn ProcessManager> = stub.clone();`
需要同时保留具体类型断言（`stub.killed()`）时，克隆一份上转。

## 批量 kill 记一条，而不是 N 条

**决策**：装饰器显式覆盖 `kill_many`，转调 inner 后记**一条**
`process.kill_many`（目标 `[3, 4, 5] (terminate)`，结果
`ok, 3 killed` / `partial, 2 failed`）。若不覆盖，trait 默认实现逐 pid
调 `self.kill`，会在装饰器层面刷出 N 条 `process.kill`——用户意图是
一次"清掉这批"，审计应反映意图。pid 列表超过 16 个截断为
`… +N more`，防止一行 JSON 撑爆。

## x capability 的探测与审计共处

**现象**：能力探测用 `service.native(&[])` 判别"这台机器有没有原生逃生
舱"（空参数在适配器里先于功能检查被拒 → InvalidInput=有该功能）。装饰
器若照单全录，`x capability` 每跑一次就留一条错误记录。

**处理**：`service.native` 仅在 args 非空时记录，代码注释写明"空参数
是特性探测，不是操作员动作"。`service.logs`、`list`、`status` 本来就
不是破坏性操作，不记录。

## 测试并发改环境变量

**现象**：audit 模块 8 个测试全部要 `set_var/remove_var` X_AUDIT /
X_AUDIT_PATH（edition 2021，API 仍安全），但 cargo 默认多线程跑测试，
别的测试可能在读同一份 env。

**处理**：`static ENV: Mutex<()>` 串行化本模块全部环境变量操作；
scratch 文件名带 `std::process::id()`，不同测试进程互不撞。默认路径
断言只查 `…/x/audit.log` 尾部，不假设本机 LOCALAPPDATA/XDG 值。

## 范围与边界

- README P0 原文写"kill、服务、防火墙…"：x 尚无防火墙域，审计覆盖现存
  四类破坏动作；未来加 firewall 时按同一装饰器模式包一层即可。
- 写入失败静默吞掉（`record_quiet`）：审计绝不能反噬被审计的操作；
  代价是"日志文件所在盘满了"这种情况无痕，属本地日志的可接受弱点。
- `X_AUDIT=off` 是全局开关，不区分操作类别；分粒度留待有真实需求。
- TUI 的 kill 天然被审计（同一 context），无需单独接线；TUI 里
  kill_many 走 `x-cli` 的 port 计划路径，同样落 `port.kill_plan`。
