# 2026-10-01 设备清单（x device）：三套枚举体系的保守合并

## 归一化只做"明确认识"的那一步

三平台的设备词汇量差了几个数量级：Windows PnP 有 100+ 个 Class
（`WPD`、`1394`、`SoftwareDevice`……），Linux 按 sysfs 目录切类，macOS
profiler 只有几棵固定树。`DeviceClass::parse` 因此只认能明确归桶的
token（usb/bluetooth/media→audio/hid→input/net…），其余一律 `Other`
并把平台原文留在 `class_raw`——归桶猜错的代价是用户按类别过滤时拿到
不相干设备，比漏报严重。中文 Windows 上「Microsoft 蓝牙枚举器」这类
本地化名原样透传，与 logs 域同一原则。

## ConvertTo-Json 的三形态又一次要全吃

`Get-PnpDevice | Select-Object … | ConvertTo-Json -Compress` 沿用
logs 域的教训：0 条是空串、1 条是对象、多条是数组，
`parse_pnp_json` 三种都接。`-PresentOnly` 保证"present"语义由 Windows
自己说，不自拼 ConfigFlags 位运算。

## sysfs：文件缺失就是字段缺失，不是空字符串

Linux 侧全部走 `read_attr`：读不到、或 trim 后为空 → `Option::None`，
序列化成 JSON 时整列缺席（`skip_serializing_if`）。两个易错点：

- `/proc/asound/cards` 的卡行和缩进详情行都以空格开头，不能用
  "行首空格"判别；以 `"]: "` 出现与否判别才对，`--- no soundcards
  ---` 占位行因此天然被跳过。
- `/sys/class/drm` 里 `card0`、`renderD128` 没有连接器语义，只保留
  名字含 `-` 的（`card0-HDMI-A-1`），status 读 `status` 属性
  （connected/disconnected 原样进 status 字段）。

## macOS USB 树限深 3 层

`SPUSBDataType` 的 children 可以套到端口级 endpoint，逐端口刷屏没有
意义；`collect_usb` 带 `USB_DEPTH_CAP`，超限不再下钻。
`SPBluetoothDataType` 新版结构以设备名为字典 key 而不是 `name` 字段，
只认 key 是 `controller_properties` 之外的 `_name/name`——蓝牙树拿不到
名字时如实返回空条目，不拿字典 key 冒充设备名（那是主机名层的结构）。
各 data type 单独 `system_profiler <type> -json`，机器上没有该硬件时
profiler 返回空根对象而非报错，解析端宽容处理。

## 交叉编译才暴露的 cfg 死引用

`use std::process::Command` 与 `use x_core::error::Error` 在 Linux
分支完全不用（Linux 不跑子进程），host 编译全绿、`--target
x86_64-unknown-linux-gnu` 直接 unused-import 拒绝——两个 import 加
`#[cfg(any(windows, target_os = "macos"))]`。另外 `filter_map(Result::ok)`
在这里吃的是 `std::io::Result`，而 `Result` 已被 x-core 别名遮蔽，
E0599 后才换成闭包 `|entry| entry.ok()`。教训：**新写 cfg 分支当晚就
跑四路交叉 clippy**，不要攒到 check.sh。

## 活体（Windows zh-CN）

`x device list` 162 台（other 109 如实兜底）；`device audio` 5 行含
Realtek/HDA；`device bluetooth` 出现「Microsoft 蓝牙枚举器」本地化原
文；`device camera` 本机无摄像头 → "no present devices of class
camera" exit 0（空不是错）；`--class bogus` exit 5 并列出可选类别。
audit.log 行数不变。
