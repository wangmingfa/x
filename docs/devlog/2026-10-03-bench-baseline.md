# 2026-10-03 · `x bench`：列表类读操作的耗时基线

对应路线图 C 组「性能基线」。`x capability` 回答「这台机器能不能读」，
`x bench` 回答「读一次要多久」，目的是让适配器悄悄变慢这件事有个能被
CI 抓住的形式。

## 决策：基线规模不能凭空造，于是把它变成一句实话

路线图写的是「本机 1000 进程 / 10k 端口规模的采样耗时基准」。真实机器上
没有 10k 个 socket 可以借：造 10k 个进程去占端口会把「测本机适配器的成本」
变成「测 x 自己造出来的负载」，测的就不是用户要跑的那条路了。所以
`x bench` 测**本机实际的规模**，再补两件让这个数字仍然有用的事：

1. **每行微秒数**：用适配器真实返回的行数归一，300 进程的笔记本和
   3000 进程的服务器因此可比（`crates/x-core/src/bench.rs:425`）。
2. **如实说明规模不够**：行数低于该目标预算假设的规模时，逐目标打印
   实际行数与基线规模，并建议**与本机历史**比较而不是与别的机器比较
   （`bench.rs:431`）。不假装绝对毫秒数是跨机器可比的。

只有「行数决定成本」的读才配基线规模：进程族 1000、socket 族 10k
（`bench.rs:129`）。interfaces / addresses / routes / disks / service 的
成本主要是固定开销（一次系统调用族、一张挂载表），给它们编一个行规模
只是把 note 变成噪音。**过滤型读也不配**：`socket list (listening)` 行数为
25 时实测 168.99 ms，与返回 124 行的整表读（171.27 ms）几乎一样——它计时的
是整张表再过滤，行数不是规模证据。这是本机实跑数据直接说出来的，不是
推理出来的。

## 决策：预算是天花板，不是性能目标

`budget_ms` 逐目标写死在 `bench.rs:103`，值故意宽松（进程整表 400 ms、
socket 整表 1000 ms、服务 3000 ms）。它要抓的量级是「每行多一次系统调用」
或「分组从线性变成平方」，不是给机器打分。`--budget-ms` 一次性覆盖全部，
`--check` 把「超预算」变成退出 1（CI 闸门）。

退出码 1 与「一般错误」共用，这属于命令特例，跟 `port check` 一样必须在
契约文档里写明白：`docs/contract.md` 的退出码一节新增一条特例。JSON 模式
`--check` 失败时**仍然只有一个文档**，超没超预算由 `status` 字段说，不再
追加散文行（`crates/x-cli/src/commands/bench.rs:94`）——确认契约里
「JSON 输出格式与突变正交」的同一条规则，用在只读命令身上就是「格式
与闸门正交」。

## 坑：中位数四舍五入会把「慢」判成「快」

表格要好看就得把毫秒数收成两位小数，但如果先四舍五入再比预算，
`--budget-ms 0` 配 0.0004 ms 的实测值会被判成 `0.00 <= 0`，即 ok。所以
`row_for` 用**未取整**的中位数判预算，只在输出字段里取整
（`bench.rs:366`，测试 `a_sub_millisecond_median_is_not_rounded_into_being_fast`）。
同理每行微秒数在 0 行时是 `None` 而不是 `0.00`：空读数打印一个「0 µs/行」
会被读成「很快」，而它真正的意思是「没有数据」（`bench.rs:423`）。

## 坑：`x ps` 的 CPU 采样窗口会冒充适配器变慢

带 usage 的进程整表读**必须**等 CPU 采样窗口（两次 refresh 之间至少
120 ms，`crates/x-platform/src/common/process_sysinfo.rs:26`），否则 CPU%
全零。实测这一项 stable 在 127 ms 上下，而 light 读是 33 ms——差值几乎
全是刻意等待。如果不说清楚，第一次跑 `x bench` 的人会以为进程适配器
比端口适配器贵 4 倍是回归。处理方式：写进 note 列（`bench.rs:143`），
表格和 JSON 里都在，不是只在文档里。

预热轮同理：`sysinfo` 的 `System` 第一次 refresh 才学到进程名，服务
管理器在第一次调用时才可能被拉起。所以每个目标先跑一轮**不计时**的
读，再跑 `--samples` 轮计时的（`bench.rs:271`）。测冷缓存会把 warm-up
当成适配器成本。

## 坑：clap 把负数当成 flag

`x bench --budget-ms -1` 不是参数错误，而是 clap 的
`unexpected argument '-1'`（退出 2，契约里保留给 clap）。写测试时踩到了：
必须写成 `--budget-ms=-1` 才能走到自己的 `Error::invalid_input`（退出 5）。
脚本里传预算时记得用等号形式，这不是 x 的规矩，是 clap 的。

## 验证

- 单元测试（与终端、与本机无关）：`crates/x-core/src/bench.rs` 13 条，
  钉住统计量、per-row 的 `None`、预算判定、失败目标不被抹成 0 行、
  规模 note 的适用范围、JSON 字段名。
- CLI 端到端：`crates/x-cli/tests/cli.rs` 7 条（`bench_*`），含
  「表格每目标一行」「JSON 是一个文档且计时是数字」「--domain 过滤」
  「--check 只在超预算时退出 1」「失败适配器保留原话」「小机器有规模
  note」「--samples 0 退出 5」。
- Windows 本机实跑：`x bench --samples 2` 11 个目标全 ok；
  `--check --budget-ms 5` 退出 1 并列出 9 个超预算目标（服务与磁盘在 5 ms
  内，故 ok——闸门没有把「预算小」误报成「全都坏了」）；`--json`、`--plain`、
  `x explain bench` 形状如上。
